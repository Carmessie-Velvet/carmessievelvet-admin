# Carmessie Velvet — Admin

Panel de administración de Carmessie Velvet (Next.js + Tailwind CSS + shadcn/ui). Es un proyecto **hermano** de [carmessievelvet-web](../carmessievelvet-web) (el storefront), pero un repo completamente aparte — sin dependencias compartidas entre ambos. El backend lo construye otro equipo, así que —igual que en el storefront— todo el consumo de datos pasa por una capa de servicios simulada (mock) en TypeScript, lista para swapear por una API REST real sin tocar la UI.

## Relación con carmessievelvet-web

- Ambos proyectos modelan el mismo dominio (productos, categorías) pero **cada uno tiene su propia copia de `types/`, `mocks/` y `services/`** — no hay paquete compartido todavía. Si el dominio crece y la duplicación empieza a doler, considerar extraer un paquete compartido (monorepo/workspace) en ese momento, no antes.
- Las categorías (`Corsets`, `Sets`) y los talles (`XS/S/M/L`) se mantienen iguales en ambos proyectos a propósito, para que los productos creados acá tengan sentido en la tienda. Catálogo real de la clienta: solo esas dos categorías (corset suelto vs. corset + falda/pantalón a juego).
- El logo real vive en `public/brand/` (mismo asset que en `carmessievelvet-web`, extraído del PDF de la clienta) — `carmessie-mark-white.png` para la sidebar oscura, `carmessie-mark-ink.png` si se necesita sobre fondo claro.

## Arquitectura de datos: mock-data-service

Mismo patrón que en `carmessievelvet-web`:
- `types/` — modelos de dominio en TypeScript puro, sin lógica.
- `services/` — interfaz (`ProductService`) + implementación mock (`MockProductService`). Los métodos de escritura (`createProduct`, etc.) hacen `console.log` del payload que se enviaría, simulan latencia de red y devuelven una respuesta falsa — así el formulario ya queda funcionalmente completo y el equipo de backend solo tiene que reemplazar el cuerpo del método por el `fetch`/`POST` real, sin tocar componentes.
- `mocks/` — datos de ejemplo (productos, categorías, colores). Nunca se importan directamente desde componentes, solo desde `services/`.

## Integración con la API real (`carmessievelvet-api`)

El backend real (`../carmessievelvet-api`, NestJS + TypeORM + Postgres + S3) ya existe. **Auth, catálogo, crear producto (con imágenes, SKU y color) están conectados a la API real.**

- **Color es un campo libre por producto, no por variante/talla** (`Product.color`, texto libre, nullable) — si el mismo diseño viene en dos colores, son dos productos/SKUs distintos en el catálogo, no una variante del mismo producto. El form de admin lo refleja como un solo input de texto ("Color") en "Información general", separado de "Stock por talla" (que sigue siendo solo `XS`/`S`/`M`/`L`, sin eje de color — nunca lo tuvo del lado del backend).
- **SKU pasó a ser el identificador de ruta** para cualquier endpoint de un solo producto — `GET/PATCH/DELETE /products/:sku` (ya no `:id`), igual en `/products/:sku/stock` y `/products/:sku/images`, y en el storefront público `/store/products/:sku`. Los listados (`GET /products`, `GET /store/products`) no cambiaron de forma. `catalogService.uploadProductImages(sku, files)` usa el `sku` del producto recién creado, no su `id` — ojo si se agrega algún otro endpoint de un solo producto, hay que seguir el mismo patrón.
- SKU es opcional al crear (`CreateApiProductPayload.sku`) — si se omite, la API genera uno (`SKU-XXXXXXXX`); si se manda, debe ser `[A-Za-z0-9-]{3,50}` (la API lo normaliza a mayúsculas). El form de admin tiene un input "SKU (opcional)" con esa misma validación en el cliente, para dar feedback antes del round-trip.
- Todo el mock original se eliminó: `services/product-service.ts`, `services/category-service.ts`, `mocks/products.ts`, `mocks/categories.ts`, `mocks/colors.ts`, y `types/product.ts` (`Category`/`Color`/`Product`/`ProductVariant`/`CreateProductPayload`). El color real es texto libre, no un catálogo predefinido, así que el mock de colores no tenía nada que aportar una vez conectada la API. Todo el dominio de producto vive ahora en `types/catalog.ts`.

Documentación completa de contratos: `../carmessievelvet-api/docs/API-FRONTEND.md` (mantenida por el equipo de backend, incluye ejemplos de request/response de cada endpoint, tabla de errores, y una sección de "limitaciones" a propósito para no asumir que algo existe cuando no).

- `src/lib/api-client.ts` — wrapper de `fetch` sobre `NEXT_PUBLIC_API_URL` (ver `.env.local`, gitignored — apunta hoy al despliegue temporal de pruebas `https://api-carmessie.spyrocode.tech/api`, va a cambiar). Desenvuelve el envelope `{success, message, data, timestamp}` / `{success:false, message, error, statusCode}` de la API y lanza `ApiError`; `message` puede venir como `string[]` (errores de validación) y se normaliza a un string. Detecta `body instanceof FormData` para no forzar `Content-Type: application/json` en la subida de imágenes (el navegador necesita poner su propio boundary de multipart).
- `src/lib/auth-store.ts` — store externo (`useSyncExternalStore`, mismo patrón que el cart de `carmessievelvet-web`) que persiste `{user, tokens}` en `localStorage` bajo `carmessie-admin-auth`.
- `src/services/auth-service.ts` (`RestAuthService`, sin mock — nunca hubo login que simular) y `src/services/catalog-service.ts` (`RestCatalogService`: `getProducts`, `getCategories`, `createProduct`, `uploadProductImages`) — todos requieren rol `ADMIN`/`SUPER_ADMIN`; `auth-context.tsx` rechaza el login client-side si el usuario no tiene ninguno de esos roles.
- `src/context/auth-context.tsx` (`AuthProvider`/`useAuth`) envuelve toda la app en `layout.tsx`. `src/components/auth/AuthGuard.tsx` protege el route group `src/app/(dashboard)/` (redirige a `/login` si no hay sesión) — `src/app/login/` vive fuera de ese grupo, sin sidebar.
- `/productos` y `/productos/nuevo` son client components (no server components) porque el JWT vive en `localStorage`, inaccesible desde el servidor sin migrar a cookies — decisión consciente para no complicar el alcance de esta integración.
- **Creación de producto** (`productos/nuevo`): `POST /api/v1/products` ya **no acepta `images` en el body** (breaking change del backend) — se crea el producto primero (nombre, precio, descripción, categoría, variantes por talla) y después, si hay imágenes, se suben aparte con `POST /api/v1/products/:id/images` (`multipart/form-data`, campo `files`, modo `append` por default). Si la creación tiene éxito pero la subida de imágenes falla, el producto queda creado sin imágenes — no hay rollback (aceptado, es un caso raro y el admin puede subir imágenes después vía Swagger/otra pantalla cuando exista).
- Las miniaturas de producto real (`/productos`) usan `<img>` plano, no `next/image` — la API puede devolver cualquier host (S3 en prod, `via.placeholder.com` de fallback), y ya nos mordió exactamente este bug con `next/image`+host no configurado en `carmessievelvet-web`.
- CORS: el backend agregó su propio `app.enableCors()` (variable `CORS_ORIGINS`, plural) — si no está seteada en el entorno, acepta cualquier origen (con warning en el log del backend). No depende de qué puerto use el dev server de este proyecto.
- Bug de Base UI encontrado y arreglado en el camino (`AppHeader.tsx`): `Menu.GroupLabel` (`DropdownMenuLabel`) exige estar dentro de `Menu.Group` (`DropdownMenuGroup`), y el item de "Cerrar sesión" usaba `onSelect` (API de Radix) en vez de `onClick` (API real de Base UI) — TypeScript no lo marcó porque `onSelect` también existe como evento nativo de `<div>`, así que compilaba pero nunca se disparaba.
- Verificado extremo a extremo contra el despliegue de pruebas real: login con credenciales reales, creación de un producto con imagen (subida y confirmada en S3), aparición en el listado, y borrado de limpieza — sin datos de prueba dejados en la instancia compartida.
- **Editar producto** (`productos/[sku]/page.tsx`): un ícono de lápiz por fila en `productos/page.tsx` lleva a esta ruta dinámica. Trae el producto (`GET /products/:sku`) y lo edita con `PATCH /products/:sku` (nombre, precio, descripción, categoría, color, SKU, estado activo/inactivo y stock por talla) — mismo form que "Nuevo producto" pero sin el campo de imágenes (esas se gestionan aparte). Si el SKU cambia al guardar, la API lo trata como una identidad nueva de ruta; la página lo detecta (`updated.sku !== currentSku`) y hace `router.replace` a la nueva URL, guardando el SKU "actual" en un state separado del param de la URL para que un segundo guardado sin recargar siga pegándole al SKU correcto.
- **Gestión de imágenes existentes** (`ExistingImagesManager.tsx`, usado solo en la página de editar): a diferencia de `ImageUploader.tsx` (que solo acumula `File[]` para subir cuando se cree el producto), acá cada acción — agregar, borrar, mover — llama a la API al instante (`POST`/`DELETE`/`PATCH /products/:sku/images`), no hay un botón de "guardar" para imágenes. Reordenar es mover-izquierda/mover-derecha (sin drag-and-drop); la primera imagen siempre es la portada.
- Bug de Base UI repetido (mismo patrón que ya nos había pasado con el `Select` de categoría): el `Select` de "Estado" (activo/inactivo) mostraba el string crudo `"true"`/`"false"` en vez de "Activo"/"Inactivo" — `SelectValue` de Base UI no resuelve la etiqueta sola, siempre hay que pasarle una función `children` que mapee el valor a su label. Cualquier `Select` nuevo en este proyecto necesita ese mismo patrón, no asumir que se resuelve solo.
- **Eliminar producto**: botón destructivo en `productos/[sku]`, `DELETE /products/:sku` (soft-delete). Confirmación con `window.confirm` nativo — no hay componente de diálogo en `ui/` todavía, se optó por el nativo del navegador en vez de instalar uno para una sola acción.

## Módulos adicionales: tags, cupones, descuentos, órdenes

Construidos para cubrir todo lo que la API ya soporta y que un admin real necesita día a día (pedido explícito del usuario: "admin robusto"). Todos siguen el estándar de diseño de arriba (tarjeta de sección con ícono, estados carga/vacío/error, badges de estado).

- **Tags** (`/tags`, `catalogService.getTags/createTag/updateTag/deleteTag`): CRUD simple de una sola página, sin ruta dinámica — crear arriba, renombrar/borrar inline por fila. `TagPicker.tsx` (chips toggle, mismo patrón visual que el viejo selector de color) se conecta en los forms de crear/editar producto vía `tagIds` — ya viaja en `CreateApiProductPayload`/`UpdateApiProductPayload`.
- **Cupones** (`/cupones`, `coupon-service.ts`) y **Descuentos de producto** (`/descuentos`, `discount-service.ts`): mismo patrón CRUD — una tarjeta de formulario que alterna entre "crear" y "editar" (`editingId` en state, sin ruta dinámica separada porque no tienen una URL pública que lo justifique, a diferencia de los productos), lista debajo con botón habilitar/deshabilitar + editar + eliminar. `code` de un cupón es inmutable una vez creado (input deshabilitado en modo edición). Los descuentos tienen selector de productos con checkboxes + filtro de texto (`endsAt` y `durationHours` son mutuamente excluyentes, validado con `.refine()` en el zod schema, igual que en el backend).
- **Órdenes** (`/ordenes` listado, `/ordenes/[id]` detalle, `order-service.ts`): el listado trae hasta 100 órdenes y filtra client-side (estado + texto), mismo patrón que el catálogo de productos. El detalle replica la máquina de estados del backend (`ALLOWED_TRANSITIONS` ∩ `MANUAL_STATUSES` en `order-status.util.ts` del API) como `NEXT_MANUAL_STATUS` en `types/orders.ts` — como el backend nunca permite saltarse un estado, en la práctica solo hay **un** botón de "siguiente estado manual" posible a la vez, nunca una lista. Cancelar pide motivo con `window.prompt` (igual que eliminar producto, sin componente de diálogo instalado). Verificado con las 2 órdenes reales de prueba que ya existían en la instancia — no se tocó su estado, son de otra sesión.
- Todas las acciones destructivas o irreversibles (eliminar tag/cupón/descuento/producto, cancelar orden) usan `window.confirm`/`window.prompt` nativos del navegador — funcionan en el navegador real, pero no son "clickeables" por herramientas de automatización que auto-descartan diálogos nativos (una limitación conocida de ese tipo de herramientas, no del código). Si en algún momento se agrega un componente `Dialog`/`AlertDialog` a `ui/`, migrar estas confirmaciones ahí en vez de seguir con las nativas.

## Productos sobre pedido y métodos de envío

La clienta pidió que las prendas se vendan **sobre pedido** en vez de por stock fijo; el backend ya lo implementó (migración `MadeToOrderProducts`) junto con un catálogo editable de métodos de envío (migraciones `ShippingMethodCatalog`/`ShippingMethodsEditable`) — checkout ahora exige elegir uno. Lo de abajo es lo que se conectó en este admin.

- **`Product.madeToOrder`** (`ApiProduct.madeToOrder`, `types/catalog.ts`): checkbox "Vender sobre pedido (sin inventario)" en la card "Stock por talla" de `productos/nuevo` y `productos/[sku]` — se manda siempre explícito en `CreateApiProductPayload`/`UpdateApiProductPayload` (nunca se depende de la inferencia por `stock` omitido que hace la API cuando el campo no viene). Cuando está activo, los inputs de stock por talla se deshabilitan (`VariantManager`'s prop `madeToOrder`) pero **no se ocultan ni se borran** — el valor se sigue guardando por si algún día vuelve a venderse con inventario real, igual que decidió el backend al no quitar la columna `stock`.
- **`ProductVariant.soldOut`** (`ApiProductVariant.soldOut`): override manual independiente del stock, uno por talla — checkbox "Agotado" junto a cada input de stock en `VariantManager.tsx`. Se administra como parte del `PATCH /products/:sku` normal (mandando `variants[].soldOut` en el array que ya reemplaza el set completo), **no** se conectó el endpoint dedicado `PATCH /products/:sku/sold-out` — hubiera sido una segunda forma de escribir el mismo dato sin aportar nada nuevo a esta UI, ya que el form de editar producto ya reescribe `variants` completo en cada guardado.
- **Listado de productos** (`productos/page.tsx`): columna "Stock" ahora muestra `Badge` "Sobre pedido" (`secondary`) cuando `madeToOrder`, o "Agotado" (`destructive`) cuando todas las variantes tienen `soldOut: true` — esta última chequea independiente de `madeToOrder` y de `totalStock`, porque un producto sobre pedido nunca tiene `totalStock` bajo (siempre es `null`).
- **`ApiProduct.totalStock`** pasó de `number` a `number | null` — la API devuelve `null` para un producto sobre pedido (no hay inventario que sumar). El listado ya no puede comparar `=== 0` como único criterio de "agotado" (ver punto anterior).
- **Métodos de envío** (`/metodos-envio`, `shipping-method-service.ts`, `types/shipping.ts`): CRUD simple de una sola página, mismo patrón visual que `/tags` — crear arriba (código + costo en MXN + descripción opcional), editar solo el costo inline por fila, eliminar (soft-delete). `code` es inmutable una vez creado (la API no tiene endpoint para cambiarlo — `ShippingMethodService` de la API solo tiene `create`/`updatePrice`, no `update`), así que no hay UI para editarlo, ni siquiera en un modo "editar". `priceMinor` viaja en centavos (iguial que Stripe); el form lo pide/muestra en pesos y convierte con `Math.round(pesos * 100)` al guardar.
- **Órdenes**: `ApiOrder` ahora trae `shippingMethod` (código elegido) y `shippingMethodDescription` (snapshot de la descripción al momento de la compra, puede no coincidir con la del catálogo actual si se editó después) — se muestran en la card "Cliente y envío" de `ordenes/[id]`. `OrderItem.madeToOrder` (snapshot de si el producto era sobre pedido al comprarse) se muestra como un `Badge` "Sobre pedido" junto al nombre del artículo en la tabla de esa misma página.
- **Checkbox nuevo en `ui/`**: `components/ui/checkbox.tsx`, wrapper de `@base-ui/react/checkbox` (mismo patrón que `select.tsx`) — se usa para `madeToOrder` y `soldOut`. Sigue el mismo criterio de estilo que el resto de `ui/` (tokens de `globals.css`, sin valores nuevos).

## Categorías con tipo y productos compuestos (sets)

La clienta pidió vender "sets" reales (una prenda arriba + otra abajo, ej. top + panty) en vez de forzarlos a la categoría `Corset` como se hacía hasta ahora. El backend lo resolvió agregando `Category.type` (`SIMPLE`/`SET`) — decide **la estructura completa** de todo producto dentro de esa categoría, nunca el nombre de la categoría ni del producto — junto con CRUD completo de categorías (antes solo lectura). Documentado a fondo en `../carmessievelvet-api/docs/API-FRONTEND.md` (secciones 5, 6, 7 y 12). Verificado en vivo de punta a punta: creación de un set de prueba con 2 prendas, confirmado en la respuesta cruda de la API, editado (renombrar una prenda) y borrado sin dejar basura en la instancia compartida.

- **`/categorias`** (nueva página, entre Productos y Órdenes en el sidebar) — CRUD completo (`catalogService.createCategory/updateCategory/deleteCategory`, mismo patrón visual que `/cupones`: una tarjeta de formulario que alterna crear/editar, lista debajo). `type` se elige en un `Select` al crear (default `SIMPLE`); la API devuelve `409` si se intenta cambiar `type` o borrar una categoría que todavía tiene productos — el mensaje de la API se muestra tal cual en el toast, no se duplica la regla en el cliente. Dos categorías semilla: `Corset` (`SIMPLE`) y `Sets` (`SET`, antes vacía).
- **`types/catalog.ts`**: nuevo `CategoryType`; `ApiCategory` ganó `type`. `ApiProductVariant` ganó `color?` (solo tiene valor real dentro de una prenda — `null`/ausente en la variante de un producto `SIMPLE`, donde el color sigue viviendo en `ApiProduct.color`). Nuevo `ApiProductComponent` (`id`, `name`, `position`, `variants`) y `ApiProduct.components: ApiProductComponent[]` (vacío para `SIMPLE`, así como `variants` queda vacío para `SET`). `Create`/`UpdateApiProductPayload.variants` pasó a opcional y ganaron `components?` — se manda exactamente uno de los dos, nunca ambos, según el `type` de la categoría elegida. Nuevos `CreateApiCategoryPayload`/`UpdateApiCategoryPayload`.
- **`components/products/ComponentManager.tsx`** (nuevo) — el equivalente de `VariantManager` para las prendas de un set, pero con una diferencia de fondo: `VariantManager` asume una grilla fija (una fila por talla, `XS/S/M/L`, sin agregar/quitar), mientras que una prenda puede repetir tallas con distinto color o tener menos/más combinaciones, así que acá **sí** hace falta agregar/quitar filas de variante (talla + color libre + stock + agotado) y agregar/quitar prendas completas (mínimo 2, solo advertido en texto — la validación dura vive en el `onSubmit` del form, ver abajo).
- **`lib/product-schema.ts`**: nuevos `componentVariantSchema`/`productComponentSchema`; `productFieldsSchema` ganó `components: z.array(productComponentSchema)` (sin `.default()` — un default ahí rompe la inferencia de tipos de `zodResolver` entre el tipo de entrada y el de salida del form). La regla "mínimo 2 prendas para un set" **no** vive en zod — el schema no sabe qué `type` tiene la categoría seleccionada, así que se valida a mano en el `onSubmit` de `productos/nuevo`/`productos/[sku]` contra `categories.find(c => c.id === categoryId)?.type`, junto con armar el payload (`components` o `color`+`variants`, nunca ambos).
- **`productos/nuevo/page.tsx`/`productos/[sku]/page.tsx`**: `categoryId` se observa con `useWatch` para derivar `isSet` contra la lista de categorías ya cargada. Si `isSet`: el campo "Color" a nivel producto se oculta (el color vive por prenda), y la card "Stock por talla" se reemplaza por "Prendas del set" con `ComponentManager` en vez de `VariantManager` — mismo patrón de composición que el resto del form (una sola `Card`, cambia su contenido, no aparece una segunda). `valuesFromProduct` (edición) mapea `product.components` (ordenados por `position`) al shape del form, con `color: v.color ?? ""` por variante.
- **`productos/page.tsx`**: `isFullySoldOut()` ahora se bifurca por `product.category.type` — un set se considera agotado cuando **todas** sus prendas lo están (cada prenda con `variants.every(soldOut)`), no cuando el producto tiene variantes propias (que para un set siempre vienen vacías). La columna "Color" ya mostraba `product.color ?? "—"`, así que un set (sin color a nivel producto) cae sola en el mismo "—" sin cambios.
- **No implementado a propósito**: imagen por prenda/color (la galería sigue siendo la del producto completo, mismo criterio que la API — ver "Out of scope for now" en `carmessievelvet-api`'s `product/CLAUDE.md`); edición de `type` de una categoría con productos (la API la rechaza con `409`, el admin solo la deja intentar y muestra el error, no bloquea el intento antes de tiempo).

## Video de producto

La clienta pidió que un producto pueda llevar un video corto opcional (máx. 10s, MP4 H.264+AAC, hasta 1080p, ~2-4 Mbps "para que sea funcional"). El backend (`AddProductVideo`, `POST`/`DELETE /products/:sku/video`, ver `../carmessievelvet-api/src/modules/product/CLAUDE.md`'s "Product video") solo valida **contenedor** (MP4/WebM, por magic bytes) y un tope de 50MB — no valida duración/resolución/bitrate, así que ese spec concreto ("si no es en ese específico no lo deja subir") se aplica **enteramente del lado del cliente**, antes de que el archivo llegue a la API.

- **`lib/product-video-validation.ts`** (`validateProductVideoFile`) — único lugar que aplica el spec: contenedor MP4 (por `file.type`/extensión, WebM queda fuera aunque la API lo aceptaría — la clienta pidió un solo formato exacto), duración ≤10s (carga metadata vía un `<video>` oculto), resolución ≤1920×1080, y bitrate aproximado (`fileSize*8/duration`) con **solo techo** (4.5 Mbps) — verificado con un encode real de ffmpeg que un video de producto típico (ropa quieta, fondo liso) comprime muy por debajo de 2 Mbps de forma legítima, así que un piso de bitrate rechazaría archivos perfectamente funcionales; lo único que de verdad importa es no dejar pasar un archivo pesado. El códec (H.264+AAC específicamente, no solo "algo que reproduzca MP4") no se puede inspeccionar desde un `File` en el navegador sin una librería de parsing (mp4box.js) que no hace falta en ningún otro lado de este admin — en su lugar se aprovecha que el propio `<video>` solo decodifica H.264+AAC (o VP8/9+Opus, ya descartado por contenedor) dentro de MP4; un codec distinto dispara el evento `error` o nunca carga metadata, y ambos casos se tratan como rechazo. Es una proxy razonable, no una garantía a nivel de bytes — documentado como tal en el archivo.
- **`components/products/VideoUploader.tsx`** (form de "Nuevo producto", un `File | null` pendiente que se sube después de crear el producto, mismo patrón que `ImageUploader`) y **`ExistingVideoManager.tsx`** (edición, sube/borra de inmediato contra la API real, mismo patrón que `ExistingImagesManager`) — ambos llaman a `validateProductVideoFile` antes de aceptar el archivo/subirlo; un archivo rechazado nunca toca la API, se avisa por toast con el motivo exacto (ej. "Dura 15.0s — el máximo es 10s.").
- **`ApiProduct.videoUrl: string | null`** (`types/catalog.ts`) + `catalogService.uploadProductVideo`/`deleteProductVideo` (`services/catalog-service.ts`, multipart `POST`/`DELETE /products/:sku/video`, mismo shape de respuesta `{productId, videoUrl}` que la API documenta). No es parte de `CreateApiProductPayload`/`UpdateApiProductPayload` — igual que las imágenes, se sube por su propio endpoint, nunca en el body del producto.
- Verificado en vivo de punta a punta contra la instancia compartida: generado un MP4 real de prueba (ffmpeg, 1920×1080, H.264+AAC, 5s) y confirmado que sube y persiste una URL real de S3 en un producto real; generado un segundo MP4 de 15s y confirmado que el validador lo rechaza antes de llegar a la API con el mensaje esperado; borrado el video de prueba al terminar para no dejar basura en el producto.

## Envíos automatizados (Enviatodo/Estafeta)

El backend agregó generación automática de guías de Estafeta (vía el proveedor Enviatodo) para órdenes `EXPRESS` — `STANDARD` sigue 100% manual como siempre. Documentado a fondo en `../carmessievelvet-api/CLAUDE.md`'s "Envíos automatizados (Enviatodo)" y `docs/API-FRONTEND.md`'s sección 18. Verificado en vivo contra el sandbox real de la clienta (una orden de prueba del equipo de backend, `CM-001062`, ya tenía una guía generada — se confirmó que el admin la lee y descarga el PDF correctamente sin generar nada nuevo).

- **Dirección estructurada en órdenes** (`ShippingAddress`, `types/orders.ts`): cambio disruptivo del backend — `line1`/`line2` desaparecieron, ahora son `street`/`extNumber`/`intNumber?`/`suburb` por separado, más `stateCode` (código de Enviatodo, no SEPOMEX/CFDI) y `state` (nombre completo, **solo lectura**, la API lo calcula). `phone` pasó de opcional a obligatorio (una guía no se puede generar sin teléfono). El admin nunca escribe una dirección de orden — solo la muestra en `ordenes/[id]` — así que el único impacto fue actualizar cómo se renderiza.
- **`ApiOrder.shipment?: ApiOrderShipment`** (`types/orders.ts`) — presente solo si ya se generó una guía para esa orden; `undefined` para toda orden `STANDARD` y para una `EXPRESS` sin guía todavía. Viene incluido en `GET /orders/:id` (no en el listado paginado `GET /orders`), así que solo se usa en el detalle.
- **Card "Guía de envío"** (`ordenes/[id]/page.tsx`): con lógica de tres estados —
  1. **Ya tiene guía** (`order.shipment` presente): muestra paquetería, número de guía, último estatus reportado por la paquetería (texto crudo tal cual lo manda Enviatodo, ej. `"GUÍA EN TRÁNSITO"` — la API no expone una versión más amable, solo la usa internamente para el email) + fecha, y un botón "Descargar guía (PDF)".
  2. **Elegible pero sin guía** (`order.status` es `PAID`/`PROCESSING`): selector de paquete (`GET /shipping/packages`, preseleccionando el que la API marca `isDefault`) + botón "Cotizar paqueterías" (`GET /orders/:id/shipment/quotes?packageId=...`) que trae `ApiShipmentQuote[]` ya ordenado de más barata a más cara — cada fila es un botón seleccionable (paquetería, servicio, tipo de transporte, fecha estimada, costo) que resalta con `border-primary` al elegirse. El botón "Generar guía" cambia su texto según haya o no una cotización seleccionada (`"Generar guía con {carrier} ({monto})"` vs. `"Generar guía (paquetería predeterminada)"`) y manda `providerId`/`providerServiceId` de la cotización elegida a `POST /orders/:id/shipment` — omitir ambos (sin cotizar, o si Enviatodo no devolvió nada) deja que el backend use su paquetería configurada por default, mismo comportamiento de antes de este cambio. Cambiar el paquete limpia la cotización (las tarifas dependen de las dimensiones). Al generarse con éxito se vuelve a pedir la orden completa (`GET /orders/:id`) en vez de confiar solo en la respuesta del POST (que es un `OrderShipmentDto`, no la orden completa) — así `status`/`trackingNumber` quedan sincronizados de una vez si la orden pasó de `PAID` a `PROCESSING`.
    - ⚠️ **Verificado en vivo (no solo documentado): una cotización con `providerId`/`providerServiceId` específicos puede dar `400` de forma pasajera** aunque esa misma paquetería apareciera segundos antes en la lista de `GET .../quotes` — la API lo documenta como un quirk conocido del sandbox de Enviatodo (`rates_client` filtrado por proveedor puede volver con `rates: []` vacío de forma intermitente). El toast de error ya muestra el mensaje de la API tal cual (mismo criterio de siempre); el admin simplemente vuelve a intentar o elige otra paquetería de la lista — no hay nada que este admin pueda hacer para evitarlo del todo, es responsabilidad del proveedor.
    - **Costo real y servicio elegido, solo para el admin**: una vez que la orden ya tiene guía, un efecto aparte pide `GET /orders/:id/shipment` (endpoint dedicado, `orderService.getAdminShipment` → `ApiAdminOrderShipment`) — más ancho que el `order.shipment` embebido (que es lo que ve el comprador, sin costo ni proveedor) — y la card agrega "Servicio"/"Costo real" cuando ese fetch resuelve. Si falla, no es crítico: la card ya muestra lo básico desde `order.shipment` sin ese fetch.
  3. **No elegible** (cualquier otro estatus sin guía): nota informativa, sin acción. No se filtra client-side por `shippingMethod` (no hay endpoint que exponga `SHIPPING_AUTOMATED_METHOD_CODES`) — si el método no está automatizado, la API responde `400 "Shipping method <code> is handled manually, not through Enviatodo"` y ese mensaje se muestra tal cual en el toast, mismo criterio que el resto del admin (confiar en el mensaje de la API en vez de duplicar la regla en el cliente).
  - ⚠️ **Quirk de sandbox, no bug**: `GET /shipping/packages` devolvió una lista vacía en las pruebas (documentado en la API como una inconsistencia conocida del proveedor — `get_package_by_id` sí funciona para el mismo id). El selector maneja esto sin romperse: sin opciones visibles, el botón "Generar guía" sigue habilitado y manda `packageId: undefined`, que el backend resuelve al default configurado (`SHIPPING_ENVIATODO_DEFAULT_PACKAGE_ID`) — no hace falta que el catálogo liste algo para que generar la guía funcione.
- **`/envios-automatizados`** (nueva página, `enviatodo-service.ts`, `types/shipping.ts`): dos cards —
  - **Dirección de origen** (`GET`/`PUT /settings/shipping-origin`): la bodega/remitente que usa Enviatodo para cotizar — es un requisito de una sola vez antes de poder generar cualquier guía (sin esto, `POST /orders/:id/shipment` da `400`). Form largo con react-hook-form + zod, mismo patrón que el form de producto; el selector de estado usa `GET /store/mx-states` (público, 32 estados con el código propio de Enviatodo — **no** coincide con SEPOMEX/CFDI en 7 estados, ver el comentario en `mx-states.const.ts` de la API). Ya estaba configurada por el equipo de backend al probar (bodega en Monterrey, NL) — se verificó que el form carga y guarda correctamente contra ese dato real.
  - **Paquetes disponibles** — CRUD completo desde que el backend agregó `POST`/`DELETE /shipping/packages` (antes era solo lectura). No existe `PATCH` (Enviatodo no lo expone de forma confiable, ver `docs/API-FRONTEND.md` de la API) — "Editar" en el diálogo (`packageFormSchema`/`onSubmitPackage`, `envios-automatizados/page.tsx`) en realidad **crea uno nuevo con los valores del form y borra el anterior**, mismo flujo que el propio backend recomienda; el copy del diálogo lo dice explícitamente para que no parezca un PATCH real. Si el borrado del anterior falla (típicamente porque era el paquete default, que `DELETE` rechaza con 409), el nuevo se agrega igual a la lista y se avisa por toast en vez de fingir que la edición fue perfecta — el botón "Eliminar" también está deshabilitado de entrada para la fila marcada `isDefault`, con un `title` explicando por qué (cambiar cuál es el default es config de backend, `SHIPPING_ENVIATODO_DEFAULT_PACKAGE_ID`, no algo que este form pueda tocar).
    - ⚠️ **El quirk de sandbox de `GET /shipping/packages` (lista) resultó ser más persistente de lo que la doc de la API sugiere** — en las pruebas de esta integración, la lista devolvió `data: []` de forma consistente (no solo "justo después de crear"), incluso para paquetes reales y verificables uno-por-uno vía `GET /shipping/packages/:id` minutos u horas después de creados. Es un bug del proveedor (Enviatodo)/su wrapper, no de este admin — pero sí tiene un parche razonable de este lado: **`enviatodoService.getPackages()` (`enviatodo-service.ts`) ya no depende solo de la lista**. `createPackage`/`deletePackage` mantienen un registro de ids conocidos en `localStorage` (`carmessie-admin-known-package-ids`, `rememberPackageId`/`forgetPackageId`), y `getPackages()` combina la respuesta de la lista con una revalidación en vivo de cada id recordado vía `getPackageById` (nunca confía ciegamente en el cache — un id que ya no exista se descarta y se limpia del `localStorage` solo). Esto arregla el caso normal (un paquete creado desde este navegador sigue viéndose después de recargar, incluido el selector de `ordenes/[id]/page.tsx`, que llama al mismo `getPackages()`), pero **es por navegador** — un paquete creado antes de este parche, o desde otro navegador/dispositivo, no aparece hasta que se vuelve a crear (o hasta que el proveedor arregle la lista de verdad). `onSubmitPackage`/`handleDeletePackage` en `envios-automatizados/page.tsx` además actualizan su propio estado local al instante con la respuesta de `POST`/`DELETE`, sin ni siquiera esperar a este mecanismo, para que la UI se sienta inmediata.
  - Ruta separada de `/metodos-envio` a propósito — son dos catálogos distintos con dueños distintos: `/metodos-envio` es el catálogo propio de esta API (`shipping_methods`, precios que cobra la tienda), esto de acá es configuración del proveedor externo (Enviatodo) para generar guías.
- **`apiFetchBlob` (`lib/api-client.ts`)**: variante de `apiFetch` para el único endpoint que no devuelve el envelope `{success, data}` — la guía en PDF (`GET /orders/:id/shipment/label`, `Content-Type: application/pdf`). Mismo manejo de 401/errores que `apiFetch`, pero al tener éxito devuelve un `Blob` en vez de parsear JSON. `downloadLabel` en `ordenes/[id]/page.tsx` arma una URL de objeto temporal y dispara la descarga con un `<a>` sintético — no hay endpoint que sirva el PDF por URL directa (se pide al proveedor en cada llamada, nunca se cachea), así que no se puede simplemente linkear.
- **No conectado a propósito**: el estatus de la paquetería lo actualiza un cron del backend cada ~30 min (no hay webhook del proveedor) — el admin no hace polling propio, solo refleja lo que ya esté en `order.shipment` cuando se carga/recarga la página. No vale la pena bajar ese intervalo desde acá; es enteramente responsabilidad del backend.

## Dashboard de estadísticas

`GET /api/v1/admin/stats/dashboard` (`types/stats.ts`, `services/stats-service.ts`) reemplazó el pie de página de "pendiente de conectar" del dashboard — ahora `/` (`(dashboard)/page.tsx`) trae ventas/órdenes/envíos/pagos/clientes/cupones/saldo Enviatodo reales, además de las métricas de catálogo que ya existían. Verificado en vivo contra la instancia compartida (69 órdenes reales, $23,722 en ingresos netos a 30 días, saldo real de Enviatodo $49,437).

- **Un solo llamado por selección de rango**: el selector de arriba a la derecha (7/30/90 días, 1 año) dispara `statsService.getDashboard({ from, to })` — la API arma las 10 secciones (`summary`, `ordersByStatus`, `sales`, `byState`, `byCategory`, `topProducts`, `shipping`, `payments`, `customers`, `coupons`, `enviatodo`) en una sola respuesta, así que no hay N llamados por sección. No se expusieron los filtros `categoryId`/`sku`/`shippingMethod`/`stateCode` que la API sí soporta — quedó fuera de este primer corte para no sobrecargar la pantalla; se puede agregar después si se pide.
- **`SalesChart` (`components/dashboard/SalesChart.tsx`)**: gráfica de **líneas** en SVG plano, sin librería (empezó como barras, ver historial de rondas de diseño abajo) — dos series, ingresos (línea sólida + relleno degradado) y número de órdenes (línea punteada), cada una **indexada 0-100% sobre su propio máximo del rango visible** en vez de compartir un eje — dos métricas de escala completamente distinta ($ vs. conteo) en un solo eje sin caer en el anti-patrón de doble eje (la skill de `dataviz` de este proyecto sanciona "indexar a una base común" como la alternativa correcta a un segundo eje Y). El tooltip (aparece con hover/foco sobre una franja invisible por punto, con una línea vertical de referencia) siempre muestra los **valores reales** ($ y conteo), nunca el índice — el índice es solo para la posición vertical del trazo. `granularity` (día/semana/mes) la resuelve la API sola según el largo del rango.
- **`ChangeBadge`**: único lugar de este admin con colores fuera de los tonos de marca (ver Tokens arriba) — verde/rojo (`text-emerald-600`/`text-red-600`, utilidades de Tailwind, no hex a mano) para el `changePct` de cada KPI vs. el periodo anterior. Es una excepción deliberada: un indicador de tendencia sin verde/rojo no se lee de un vistazo, y ninguno de los tonos de marca (velvet/velvet-light/sand) comunica "bien"/"mal" por sí solo; si se necesita este patrón en otra pantalla, reusar esta misma paleta en vez de inventar una nueva.
- **⚠️ `shipping.margin` se muestra marcado como "(preliminar)"**, con una nota fija debajo de la card explicando por qué: la API sí devuelve el campo, pero hoy `charged` suma el envío cobrado de **todas** las órdenes del periodo mientras que `cost` solo suma lo que Estafeta cotizó en las que tienen guía automática — no son la misma población, así que `margin = charged - cost` no es un margen real todavía (encontrado en code review de `f7e208c`, reportado al equipo de backend). Quitar el `(preliminar)` y la nota cuando el backend confirme que lo corrigió — no antes.
- **`refreshing` en vez de un spinner nuevo por cada refetch**: cambiar el rango no reemplaza la pantalla por un loader — el dashboard anterior se queda visible a `opacity-60` mientras llega el nuevo (regla de la skill de dataviz: "refetch keeps the frame"). El `useState(true)` inicial (no un `setState` síncrono dentro del `effect`, que el lint de este proyecto rechaza — ver el mismo patrón resuelto con `useWatch` en el form de producto) es lo que hace que la primera carga sí muestre el spinner grande de "cargando".
- Las métricas de catálogo (arriba del todo) siguen viniendo de `catalogService`, no de este endpoint — son cosas distintas (inventario actual vs. histórico de ventas) y la API de stats no reemplaza esa sección.
- **Segunda pasada de diseño** (pedido explícito del usuario, con una captura de referencia tipo dashboard e-commerce — crema/naranja, íconos coloridos, números grandes). Pasó en dos rondas:
  1. Primera ronda: adoptar solo la *estructura* (más tipos de gráfica, tarjeta de KPI destacada, desgloses proporcionales en vez de listas de números) sin tocar la paleta — el usuario eligió esto explícitamente la primera vez.
  2. El usuario volvió a pedir "algo más vistoso" citando que la clienta es joven y valora el diseño más que un tono serio — en esa segunda ronda sí se sumó color: **`--velvet-light`/`--sand`** (Tokens arriba), aplicados en gráficas y chips de ícono, más números en `font-extrabold`, esquinas más redondeadas (`--radius` subido) y el patrón de ícono extraído a `SectionIcon` y llevado a **toda la app**, no solo el dashboard (pedido explícito: "aplica los cambios visuales de una vez en todo el admin").

La leyenda con el valor de cada porción siempre está visible al lado, nunca solo al hover. El acumulado de ángulos se calcula con un `reduce` puro (un prefix-sum en un array nuevo), no con una variable mutada entre iteraciones — el lint de este proyecto (`react-hooks/immutability`, parte del compilador de React) rechaza reasignar una variable de cierre dentro de un `.map`.
  - **`SegmentedBar` (`components/dashboard/SegmentedBar.tsx`)**: una barra horizontal única dividida proporcionalmente (mismo `chartColor()` que `DonutChart`) + una lista debajo con el % de cada segmento — para cualquier "esto vs. aquello" donde la proporción importa más que el número absoluto solo. Se reusa en: cobertura de guía automática y método de envío (card Envíos), método de pago e invitados/nuevos vs. registrados/recurrentes (cards Pagos/Clientes).
  - **`MetricTile` con `hero`**: la tarjeta de "Ingresos netos" lleva un degradado `from-primary/12 via-primary/5 to-velvet-light/10` de fondo + ícono con degradado `from-primary to-velvet-light` (antes era un tinte plano `bg-primary/5` de un solo tono) — mismo tratamiento de "tarjeta destacada" que la referencia, con los dos tonos reales de marca. Las otras tres tarjetas de KPI ciclan `SECTION_ICON_TINTS` igual que el resto de la app.

  - **`SectionIcon` (`components/ui/section-icon.tsx`)**: extraído de `page.tsx` en la segunda ronda y llevado a **toda la app** (`ordenes/[id]`, `productos/nuevo`, `productos/[sku]`, `tags`, `cupones`, `descuentos`, `metodos-envio`, `envios-automatizados`) — reemplaza el `<span>` de ícono que antes se copiaba literal en cada archivo (ver "Patrones de composición" arriba). `SECTION_ICON_TINTS` (también exportado de ahí) cicla los tres tonos de marca; `chart-colors.ts` es su equivalente para marcas de dato en gráficas (dos archivos separados porque un chip de ícono y una porción de gráfica tienen reglas de contraste distintas — ver el punto de `--sand` arriba).
- **Tercera ronda — réplica literal del layout de la referencia.** Después de la segunda ronda el usuario seguía sin convencerse: quería el **mismo diseño** de la captura (mismo acomodo de tarjetas, mismos tipos de gráfica — línea, gauge, funnel de columnas, barra segmentada, dona + lista con barras), no una interpretación libre — "solo adaptado a nuestros colores y datos". Esta ronda reconstruyó el bloque "hero" del dashboard para calzar 1:1 con esa referencia, con datos 100% reales (nunca se inventó una etapa/métrica que la API no expone):

Si se reordena o se agrega una tarjeta al bloque hero, el span de cada una (no el de sus vecinas) es lo único que hay que ajustar.
  - **`GaugeChart` (`components/dashboard/GaugeChart.tsx`)**: medidor de media dona (arco de 180°, no un círculo completo) — equivalente al "Monthly Target" de la referencia. Mapeado a la **tasa de conversión pagadas/creadas** (`payments.conversionRate`), el único "% de una meta" que existe de verdad en la API — nunca se inventó una meta de ventas. Dos cajas tintadas debajo (Creadas/Pagadas) replican las cajas Target/Revenue de la referencia.
  - **`FunnelColumns` (`components/dashboard/FunnelColumns.tsx`)**: reemplazó a `FunnelRow` (barras horizontales) — ahora son columnas de altura decreciente con el valor arriba y el % del primer paso debajo, igual que el "Conversion Rate" de la referencia. Sigue siendo solo "Creadas → Pagadas" (los únicos dos pasos donde uno es de verdad subconjunto del anterior) — **no** se usó la distribución de `ordersByStatus` para esto: esos 7 estatus son mutuamente excluyentes (el estado *actual* de cada orden), no una cadena de abandono acumulada, así que graficarlos como funnel habría sido engañoso.
  - **"Métodos de envío"** (segmentada, por número de órdenes) hace de "Traffic Sources" de la referencia — movida al bloque hero; el detalle de cobrado/margen/cobertura de guía se quedó en su propia card "Envíos" más abajo, sin repetir el mismo desglose por método dos veces.
  - **Animaciones** (pedido explícito: "meter animaciones que hagan más vistoso y mejore la UX"), todas en `src/hooks/use-revealed.ts` (`useRevealed`) y `src/hooks/use-count-up.ts` (`useCountUp`), reusadas por los componentes de `components/dashboard/`:
    - `useRevealed()`: `false` en el primer render, `true` un par de `requestAnimationFrame` después — el truco estándar para que una transición CSS sí anime de "0 → valor real" en vez de aparecer ya en su posición final.     - `useCountUp(target)`: anima un número de su valor anterior al nuevo en ~700ms con ease-out cúbico — puramente cosmético (nunca cambia el valor final ni pasa por un estado intermedio inventado). Se usa en `StatCard`, `MetricTile` y el `%` central de `GaugeChart`.
    - `Reveal` (`components/dashboard/Reveal.tsx`): envoltura genérica de fade+slide-up para las 9 tarjetas del bloque hero, con `delayMs` creciente (0, 60, 120...) para que entren en cascada en vez de todas a la vez.
    - `CARD_HOVER` (constante en `page.tsx`, `transition-[transform,box-shadow] duration-200 hover:-translate-y-0.5 hover:shadow-md`): mismo levantamiento sutil en **todas** las `Card` de esta pantalla al pasar el mouse — no es exclusivo del bloque hero.
    - Nada de esto usa una librería de animación nueva — todo es CSS transitions/clip-path + `requestAnimationFrame`, consistente con "sin librería" del resto de `components/dashboard/`.

## Cuarta ronda de diseño — sidebar/topbar claros + limpieza de redundancias (todo el admin)

Pedido explícito con otra captura de referencia (mismo dashboard EzMart de la ronda 3, esta vez pidiendo el **shell** — sidebar y topbar — no solo las gráficas): "quiero que el navegador de hamburguesa... se vea igual, solo usando nuestros colores" + "aplica este diseño a todo el admin". A diferencia de las rondas 1-3 (solo `page.tsx` del dashboard), esta se aplicó en los componentes **compartidos** por toda la app, así que se propaga a cada ruta sin tocarlas una por una:

- **`globals.css`**: `--background` pasó de blanco puro a un tostado muy claro (`oklch(0.98 0.006 55)`, el mismo tinte cálido de `--sand` pero muchísimo más aclarado — no un color nuevo) para que las cards blancas resalten encima, igual que en la referencia. Los tokens `--sidebar*` se reescribieron de cero: el sidebar oscuro por defecto de shadcn (`oklch(0.145 0 0)`) pasó a blanco puro (`oklch(1 0 0)`, igual que las cards), `--sidebar-foreground` a `var(--muted-foreground)` (gris medio para los ítems inactivos, como la referencia) y `--sidebar-accent`/`-border` a tintes tostados sutiles solo para el hover — el estado **activo** no usa `--sidebar-accent` (ver siguiente punto).
- **`components/ui/card.tsx`**: la sombra + el hover-lift (`shadow-sm`, `hover:-translate-y-0.5 hover:shadow-md`) que antes vivían en la constante local `CARD_HOVER` del dashboard (`page.tsx`) se movieron al `Card` base — así **toda** tarjeta de **toda** la app (productos, órdenes, cupones, etc., no solo el dashboard) flota igual sobre el fondo tostado. La constante `CARD_HOVER` y sus ~15 usos en `page.tsx` se eliminaron por quedar redundantes.
- **`components/layout/AppSidebar.tsx`**: el ítem de nav activo ya no depende de `--sidebar-accent` — se pinta a mano con `!bg-primary !text-primary-foreground` (el `!important` gana pase lo que pase con el orden de las clases generadas por Tailwind) para que se vea como una pastilla sólida en el color de marca, igual que el naranja de la referencia. El copy de `STATUS_GUIDE` no es interpretación propia — es una traducción directa a español llano de la explicación que dio el equipo de backend (Efren Almanza, mensaje del 5/9/26): "en preparación" es trabajo humano (buscar/revisar/empacar la prenda), generar la guía dispara sola el paso a "en proceso" si la orden seguía en "pagada", y de ahí en adelante (enviada/entregada) el estatus lo mueve solo el sistema según lo que reporte Estafeta — **todo esto solo aplica a envíos `EXPRESS`**, `STANDARD` sigue siendo 100% manual (el admin marca los estatus a mano con los botones que ya existían).

En mobile/tablet (`grid-cols-1`) se apila debajo de todo lo demás — no hay espacio para un panel fijo en una pantalla angosta, y forzarlo ahí sería peor que dejarlo al final.

**El botón manual de "siguiente estatus" ahora respeta el método de envío** (`isAutomatedShipping()`, `types/orders.ts` — mirror del `SHIPPING_AUTOMATED_METHOD_CODES` del backend, hoy solo `EXPRESS`; solo decide qué controles mostrar, la autoridad real sigue siendo el rechazo de la API): antes el botón "Marcar como X" (`NEXT_MANUAL_STATUS`) se mostraba igual para cualquier orden, y "Generar guía" era una acción aparte en su propia tarjeta — un admin podía avanzar una orden EXPRESS a mano sin pasar por Enviatodo, o generar una guía sin que eso fuera lo que movía el estatus. - En `PAID`, el botón manual se oculta — la única acción es "Generar guía" (tarjeta "Guía de envío"), que en el backend (`ShipmentService.create`) ya mueve `PAID → PROCESSING` en el mismo request, así que generar la guía **es** avanzar el estatus.
- En `PROCESSING`/`SHIPPED`, no hay ningún botón manual — un texto explica que el estatus avanza solo según lo que reporte Estafeta (`ShipmentPollingService`, cada ~30 min) — mostrar "Marcar como Enviada/Entregada" ahí sería una acción que además rompería lo que el cron ya hace.
- La tarjeta "Guía de envío" también dejó de ofrecer "Generar guía" para un método no automatizado (STANDARD) — antes el botón aparecía para cualquier orden `PAID`/`PROCESSING` sin guía y solo fallaba al hacer clic (400 del backend, "handled manually, not through Enviatodo"); ahora directamente explica que ese método se gestiona a mano.
- Para STANDARD, nada cambió: sigue siendo el botón manual + input de tracking de siempre.

**Paquetería en envíos manuales** — el backend agregó `carrier` (`Order.carrier`, migración `AddCarrierToOrders`): se llena por snapshot desde el catálogo (`ShippingMethodOption.carrier`, ej. "Correos de México"/"Estafeta") al momento de la compra, pero un admin puede sobreescribirlo por orden vía `PATCH /orders/:id/status` sin tocar `/metodos-envio`. En `ordenes/[id]/page.tsx`, junto al input de "Número de rastreo" que ya existía para el flujo manual (STANDARD) al marcar como `SHIPPED`, ahora hay un segundo input "Paquetería" — precargado desde `order.carrier` (`types/orders.ts` ganó el campo), se manda junto con `trackingNumber` en `orderService.updateOrderStatus(id, status, trackingNumber, carrier)`. Se muestra en modo lectura en dos lugares: junto al rastreo en la card "Estado del pedido" (`Rastreo: XXX (Correos de México)`) y en la card "Cliente y envío" (`Paquetería: ...`) — solo si `order.carrier` existe, nunca un placeholder vacío. No aplica a envíos automatizados (`EXPRESS`) — ahí la paquetería la fija el snapshot de compra o `POST /orders/:id/shipment`, sin input manual.

## Devoluciones y reembolsos parciales

El backend agregó `PARTIALLY_REFUNDED` como estatus terminal, `refundMode`/`amount` en `POST /orders/:id/cancel`, y todo el flujo de solicitudes de devolución post-entrega (`OrderReturnRequest`) — documentado a fondo en `../carmessievelvet-api/CLAUDE.md`'s "Orders & checkout" y `docs/API-FRONTEND.md`'s sección 20. Verificado en vivo de punta a punta: mandé dos solicitudes reales vía `POST /store/orders/return-request` (el mismo endpoint público que usaría el storefront, llamado a mano desde la consola ya que el storefront de devoluciones no es parte de este repo), aprobé una (quedó `PARTIALLY_REFUNDED`, `refundedAmount` correcto) y rechacé la otra (la orden no se tocó, solo la solicitud).

- **`types/orders.ts`**: `OrderStatus` ganó `PARTIALLY_REFUNDED`; nuevos tipos `RefundMode` (`FULL`/`FULL_MINUS_SHIPPING`/`PARTIAL`) y `ReturnRequestStatus` (`PENDING`/`APPROVED`/`REJECTED`) + `ApiReturnRequest`. `ApiOrder` ganó `refundedAmount` (siempre presente, `0` hasta el primer reembolso) y `returnRequest?` (solo en lecturas de una sola orden, ver abajo). `statusBadgeVariant()` se centralizó acá (antes vivía copiado y pegado en `page.tsx`, `ordenes/page.tsx` y `ordenes/[id]/page.tsx` — los tres ahora importan la misma función) para no tener que acordarse de actualizar tres copias cada vez que se agrega un estatus nuevo, como aquí.
- **`components/orders/RefundDialog.tsx`** (nuevo, compartido): un solo diálogo para las dos acciones que terminan llamando `POST /orders/:id/cancel` — "Cancelar orden" desde el detalle, y "Aprobar devolución" desde `/devoluciones` o desde la card de solicitud en el detalle. Pide motivo (obligatorio, textarea) siempre; si la orden ya se pagó (`status !== "PENDING"`) también pide `refundMode` (select) y, solo si es `PARTIAL`, un monto en pesos — si la orden nunca se pagó, oculta esos dos campos y avisa que se cancelará sin reembolso, igual que el backend los ignora en ese caso. `defaultRefundMode` es configurable por el caller: el detalle de orden usa `FULL` (default del backend) para "Cancelar orden" normal, pero `FULL_MINUS_SHIPPING` para "Aprobar devolución" — es el modo que la política de la tienda espera para una devolución post-entrega (el comprador paga el envío de vuelta, no la tienda).
- **`/devoluciones`** (nueva página, en el sidebar entre Órdenes y Cupones) — la cola de solicitudes sin resolver (`GET /orders?returnRequestStatus=PENDING`). ⚠️ **`returnRequest` no viene poblado ni en este listado filtrado** (confirmado en vivo, no solo documentado) — solo trae qué órdenes tienen una solicitud pendiente, no el motivo/fecha. La página pide el detalle completo de cada una (`Promise.all` de `getOrder(id)`) antes de pintar la tabla — mismo patrocinio que `shipment`, que tampoco viene en el listado paginado. Sin fila de stats arriba a propósito (mismo criterio que Cupones/Descuentos/Tags/Métodos de envío): la lista completa ya es la cola entera, un contador no aporta nada que el título no diga ya.
- **`ordenes/[id]/page.tsx`**: nueva card "Solicitud de devolución" (solo si `order.returnRequest` existe) — si está `PENDING`, botones "Aprobar (reembolsar)" (abre `RefundDialog`) y "Rechazar" (un `prompt()` de `useConfirmDialog`, ya que solo pide un motivo — no hace falta el diálogo completo); si ya se resolvió, muestra la nota/modo de reembolso/fecha en modo lectura. El botón genérico "Cancelar orden" de la card de estado también pasó de `prompt()` a `RefundDialog` — ahora sí permite elegir `refundMode`/monto en vez de solo mandar `reason` (antes el reembolso, si la orden ya estaba pagada, siempre era `FULL` sin que el admin pudiera elegir otra cosa).
- **Dashboard**: nuevo StatCard "Devoluciones pendientes" (mismo `GET /orders?returnRequestStatus=PENDING`, solo se necesita `.length` así que no hace falta el `Promise.all` por-orden de `/devoluciones`) en la fila de catálogo, enlazado a `/devoluciones`, con tono de advertencia si hay alguna pendiente — la fila pasó de `sm:grid-cols-4` a `sm:grid-cols-5` para acomodarlo.
- **No implementado a propósito**: la pantalla pública de "solicitar devolución" (`POST /store/orders/return-request`) — vive en el storefront (`carmessievelvet-web`), no en este admin. Este repo es 100% el lado ADMIN del flujo (ver/aprobar/rechazar), nunca el lado del comprador.

## Bug pre-existente encontrado (no de este cambio): descripción vacía bloquea guardar

Al probar el toggle de `soldOut` contra un producto real se encontró que **cualquier producto cuya `description` haya quedado vacía en la API no se puede editar desde este admin** — `productFieldsSchema` (`product-schema.ts`) exige `description.min(10)` en ambos forms (crear y editar), pero `valuesFromProduct` rellena el campo con `product.description ?? ""` cuando la API no tiene descripción guardada, así que el form arranca ya inválido y cualquier intento de `Guardar cambios` falla la validación de zod sin dar pista de por qué (el error solo aparece bajo el textarea, fácil de no notar si se scrollea de más). No se tocó en esta sesión por estar fuera de alcance del pedido — hay que decidir si `description` deja de ser obligatoria en el form de edición (la API sí la trata como opcional) o si se exige rellenarla al vuelo la primera vez que se edita un producto legado sin ella.

## Lo que le falta a la API para un admin realmente completo

Encontrado mientras se construía lo de arriba — no es responsabilidad de este repo arreglarlo, pero vale la pena pedirlo al equipo de backend:

**Alto impacto (bloquean operación diaria real):**
1. **Notificaciones al cliente** (al menos email): confirmación de orden, pago confirmado, envío con tracking, cancelación/reembolso. Hoy no se manda nada — ya está documentado como límite conocido en `API-FRONTEND.md`, pero sigue siendo el gap más grande para operar de verdad.
2. **Gestión de clientes para el admin**: no hay `GET /users` ni nada similar — el admin solo ve nombre/email dentro de cada orden, no un perfil de cliente ni su historial agregado de compras.
3. **Limpieza de órdenes `PENDING` abandonadas**: ya vimos 2 reales en la instancia de pruebas (nunca se completó el pago). No hay barrido automático ni un endpoint para cancelarlas en bulk — se acumulan para siempre salvo que un admin las cancele una por una.
4. **Cálculo de envío real**: `shippingTotal` siempre es `0` — no hay forma de cobrarlo.
5. **Reportes/analítica**: no hay ningún endpoint de ventas por período, productos más vendidos, etc. — el dashboard del admin solo puede mostrar conteos del catálogo (productos/categorías), nunca métricas de negocio, por más que se rediseñe el frontend.

**Impacto medio:**
6. **Auditoría de órdenes expuesta**: `order_status_history` existe en la base de datos pero no hay endpoint para leerlo — el admin no puede ver quién cambió un estado y cuándo.
7. **Categorías editables**: hoy son solo seed (`Corset`, `Sets`) — si la clienta pide una tercera categoría, se necesita una migración de backend, no hay `POST /categories`.
8. **Reembolsos parciales**: `POST /orders/:id/cancel` siempre reembolsa el 100%, documentado como decisión de v1.
9. ~~Preview de cupón sin comprar~~ — **resuelto**: `POST /api/v1/store/coupons/validate` (público) ya existe. Sigue sin ser una función de admin (es para el carrito del storefront), pero queda anotado en la sección de abajo.
10. **Import/export masivo de productos** (CSV): cargar o actualizar el catálogo hoy es producto por producto.

**Bajo impacto / a futuro:**
11. Umbral configurable de "stock bajo" (hoy el dashboard solo distingue 0 contra más de 0, no hay forma de avisar "quedan 2").
12. CDN/optimización de imágenes (hoy son URLs directas de S3, sin transformar).
13. Reseñas de producto — sigue sin existir. La lista de deseos ya no aplica: ver módulo de wishlist abajo.

**No es un gap de backend, es una decisión nuestra**: la API sí tiene `/api/v1/roles` completo (crear/editar roles, asignar roles a usuarios, `SUPER_ADMIN` únicamente) pero no se construyó pantalla para eso en el admin — quedó fuera a propósito por ser una función sensible y poco usada. Se puede agregar después si hace falta promover admins desde la UI en vez de por base de datos.

## Cambios de la API revisados y no aplicados a este admin (a propósito)

Una tanda de cambios agregó wishlist, preview de cupón y rate-limiting de login. Revisados uno por uno:

- **Wishlist** (`/api/v1/me/wishlist`, `@Roles(UserRole.USER)`) — función de cliente final (guardar productos favoritos en el storefront), no existe ningún endpoint admin-facing sobre esto (ej. "productos más deseados"). No hay nada que agregar acá; es 100% para `carmessievelvet-web`.
- **Preview de cupón** (`POST /api/v1/store/coupons/validate`, público) — pensado para el carrito del storefront ("este cupón te da $X de descuento" antes de pagar). Se podría agregar un botón "Probar cupón" en `/cupones`, pero requeriría armar un carrito de prueba (`productId`+`size`+`quantity`) solo para validar un código — la fricción no vale la pena hoy; el admin ya ve `isCurrentlyValid` en cada cupón, que es la parte que sí importa para administrar. Reconsiderar si algún día hace falta simular carritos reales desde el admin.
- **Rate limiting de login** — sí aplica directo: `POST /auth/login` ahora cuenta intentos fallidos (nunca los exitosos) y bloquea con `429` tras 5 fallos por IP o 10 por email en 15 minutos, por otros 15 minutos. `ApiError` (`api-client.ts`) ahora carga `retryAfter` (segundos) cuando el body del error lo trae, y `login/page.tsx` lo muestra en español ("Probá de nuevo en N minutos") en vez del mensaje genérico. **No se probó disparando el límite de verdad** — el bloqueo es por IP, así que hubiera tumbado el login real por 15 minutos en la instancia compartida; se verificó por build/tipos únicamente.
- El refactor de `ProductFilterQueryDto` (filtros de catálogo compartidos entre admin/storefront/wishlist) es reorganización interna del backend — no cambia la forma de `GET /api/v1/products` que ya consume `catalogService`, no hizo falta tocar nada acá.

## Estándar de diseño

Regla general: **toda pantalla o componente nuevo sigue estos patrones** — son los mismos que ya usan `page.tsx` (dashboard), `productos/page.tsx` y `productos/nuevo/page.tsx`. Si una pantalla nueva necesita algo que no está aquí, extender el sistema (mismos tokens, misma lógica de composición) en vez de inventar uno paralelo, y si el patrón es reutilizable, agregarlo a esta lista.

- **Audiencia**: equipo interno (no clientas) — pero la dueña de la marca es joven y valora el diseño, así que el tono es **funcional pero vistoso**, no genérico ni corporativo-aburrido (pedido explícito de la clienta, con una captura de referencia tipo dashboard e-commerce como norte — ver "Segunda pasada de diseño" en la sección del dashboard más abajo). Sigue siendo **desktop-first pero responsive**, y sigue sin ser editorial (no mayúsculas/mobile-first estricto del storefront).
- **Aire de familia con el storefront**: misma familia tipográfica y ahora también **dos** tonos de marca compartidos con `carmessievelvet-web` (ver Tokens abajo) — es intencional que ambas apps se sientan de la misma marca. Lo que **no** se copió: la paleta cálida de neutros del storefront (crema/tinta, `--color-cream`/`--color-ink`) ni el mobile-first estricto — el admin sigue sobre grises neutros, no cálidos.

### Tokens (no inventar valores nuevos — están en `src/app/globals.css`)

- **Colores de marca**: `--primary` / `--ring` / `--sidebar-primary` = `#4b1530` (velvet, mismo hex que `--color-velvet` del storefront) sigue siendo el acento principal (botones, links, estados). Desde la segunda pasada de diseño se agregaron **dos tonos más**, también tomados tal cual del storefront (`--color-velvet-light`/`--color-sand` en su `globals.css`): `--velvet-light` (`#8c4a63`) y `--sand` (`#dccfbf`) — se usan **solo como acento decorativo** (chips de ícono, gráficas del dashboard), nunca en botones/links/estados, que siguen siendo 100% `--primary`. Si hace falta un cuarto tono en algún momento, usar uno de los que ya existen en `carmessievelvet-web` antes que inventar uno nuevo — la regla no es "un solo acento" sino "solo los acentos que ya son de la marca".
- **Neutros**: el resto de la paleta (`--background`, `--card`, `--muted`, `--border`, etc.) son grises `oklch` de shadcn — **a propósito no** los cálidos del storefront (crema/tinta) — no hardcodear hex, usar las clases (`bg-muted`, `text-muted-foreground`, `border-border`, `bg-destructive/10 text-destructive`, etc.).
- **Radios**: `--radius: 0.65rem` como base (antes `0.5rem` — se subió en la segunda pasada de diseño para que todo se sintiera un poco más suave/vistoso; es un solo número, cascada a todo `radius-sm..4xl`, no hubo que tocar componentes). `rounded-lg` para inputs/botones/tablas, `rounded-xl` (default de `Card`, y de `SectionIcon` — ver Iconografía) para tarjetas/chips de ícono. No usar `rounded-full` salvo círculos reales (avatares, badges de ícono redondos, dots de leyenda).
- **Sidebar**: oscura y fija (`Sidebar collapsible="icon"`), independiente de la paleta clara del contenido — no cambiar sus tokens (`--sidebar-*`) para que combinen con el contenido; es intencional el contraste.

### Tipografía y jerarquía

- **Título de página**: `text-2xl font-semibold tracking-tight` + subtítulo `mt-1 text-sm text-muted-foreground`. Siempre este par, sin ícono al lado del `h1` — el ícono va en las tarjetas de sección, no en el título de página (ver abajo).
- **Título de tarjeta/sección**: `CardTitle` (ya trae `text-base font-medium`) + `CardDescription` (`text-sm text-muted-foreground`) debajo.
- **Números grandes de dato** (KPIs, stats del dashboard): `text-3xl font-extrabold` — única excepción al "nada de extra-bold" de abajo, porque un número es la protagonista de esa tarjeta y necesita peso visual (pedido explícito de la clienta al ver la referencia). No aplica a `CardTitle` normal (nombres de sección), solo al valor numérico en sí (`StatCard`/`MetricTile` en `page.tsx`).
- **Texto de apoyo/nota**: `text-xs text-muted-foreground` para aclaraciones al pie de una pantalla (ver el pie del dashboard o del form de producto).
- Una sola familia tipográfica en toda la app — no introducir una segunda sin que lo pida el negocio. Es **Archivo** (`next/font/google`, variable `--font-sans` en `layout.tsx`), la misma que usa `carmessievelvet-web`. A diferencia del storefront (que la usa en `font-black uppercase tracking-tight` para headings, eco del logo), acá se usa en pesos normales/semibold para texto y `font-extrabold` solo para números de dato (ver punto de arriba) — nunca mayúsculas, eso sigue siendo parte del tono editorial que este admin no adopta.

### Iconografía

- Solo `lucide-react`, estilo stroke, nunca emoji ni glifos decorativos.
- Tamaño `size-4` dentro de botones/badges; `size-5` en estados vacíos/carga; `size-9` es el tamaño del contenedor de ícono de sección (ver "tarjeta de sección" abajo), con el ícono en `size-4` adentro.
- **Los chips de ícono ya no son todos del mismo tono** — antes cada uno era `bg-primary/10 text-primary`; desde la segunda pasada de diseño ciclan entre los tres tonos de marca (`SECTION_ICON_TINTS`, ver abajo) para que la pantalla se sienta más viva sin salirse de la paleta de Carmessie.

### Patrones de composición (copiar la forma, no solo el resultado)

- **Encabezado de página**: `<div className="flex items-center justify-between">` con el título+subtítulo a la izquierda y la acción primaria (`Link`/`Button`) a la derecha. Ejemplo: `productos/page.tsx`.
- **Tarjeta de sección con ícono** (todas las pantallas del admin): `<SectionIcon icon={Icon} index={n} />` (`components/ui/section-icon.tsx`) dentro de `CardHeader`, seguido de `CardTitle`/`CardDescription`. Antes esto era un `<span>` copiado literal en cada archivo (`bg-primary/10` fijo); se extrajo a un componente compartido en la segunda pasada de diseño porque ahora el color cicla (`index` = posición de la tarjeta en la pantalla, en el orden en que aparecen — no aleatorio, para que el patrón de color sea predecible). **Toda tarjeta de sección nueva debe usar `SectionIcon`, no volver a escribir el `<span>` a mano.**
- **Tarjeta de estadística** (`StatCard`/`MetricTile` en `page.tsx`, el dashboard): mismo `SectionIcon` de arriba pero con el valor grande (`text-3xl font-extrabold`, ver Tipografía) como "título". Usar `tone="warning"` (fondo/texto `destructive`) solo para métricas que de verdad requieren atención (ej. sin stock), nunca decorativo. **Nunca inventar una métrica que no venga de una llamada real a `catalogService`/`statsService`** — si el dato no existe todavía, no se muestra, no se pone en 0 falso ni se simula: se documenta como pendiente.
- **Tabla de listado** (`productos/page.tsx`): thumbnail 40px (`size-10 rounded-md bg-muted overflow-hidden`, `<img>` plano — ver regla de imágenes abajo), nombre en `font-medium` con el identificador secundario (SKU) debajo en `text-xs text-muted-foreground`, columnas descriptivas en `text-muted-foreground`, estado como `Badge`.
- **Búsqueda de tabla**: `Input` con ícono `Search` absoluto a la izquierda (`pl-8` en el input, ícono en `absolute left-2.5 top-1/2 -translate-y-1/2`), filtro client-side sobre los datos ya cargados — no agregar un endpoint de búsqueda mientras el catálogo quepa en una sola página (`limit=100`).
- **Estados de carga/vacío/error** (mismo trío en cualquier pantalla que lea de la API):
  - Cargando: `<Loader2 className="size-5 animate-spin" />` centrado, con texto de apoyo en el subtítulo de la página ("Cargando... desde la API").
  - Vacío (sin datos todavía, no por filtro): caja `border border-dashed border-border` con ícono en círculo muted, mensaje + CTA si aplica.
  - Vacío por filtro (búsqueda sin resultados): misma caja punteada pero sin ícono/CTA, solo el texto "Ningún... coincide con...".
  - Error: `rounded-lg border border-destructive/30 bg-destructive/5 px-4 py-3 text-sm text-destructive`.
- **Badges de estado**: `Badge` con `variant="default"` (activo/ok), `variant="secondary"` (inactivo/neutral), `variant="destructive"` (agotado/atención) — nunca texto suelto en rojo (`text-destructive`) para indicar estado cuando existe el badge; el texto suelto se reserva para mensajes de error de formulario/página.
- **Formularios largos**: una `Card` por sección lógica (ver `productos/nuevo`), cada una con su tarjeta-de-sección-con-ícono como header, campos cortos en pareja (`grid grid-cols-1 gap-4 sm:grid-cols-2`), acciones (Cancelar/Guardar) alineadas a la derecha al final del form, nunca dentro de una `Card`.

### Reglas duras

- **Imágenes que vienen de la API**: siempre `<img>` plano, nunca `next/image` — la API puede devolver cualquier host (S3, o su placeholder `via.placeholder.com`) y `next/image` corta la app con un host no configurado en `remotePatterns`. Esto ya rompió `carmessievelvet-web` una vez; no repetirlo acá.
- **`CardHeader` es un CSS grid, no un flex** (`display: grid` en `card.tsx`) — `items-center` ahí solo centra verticalmente (`align-items`). Para centrar horizontalmente un ítem (ej. un logo en un header centrado, como en `login/page.tsx`) hace falta `justify-items-center` explícito además de `items-center text-center`, porque un elemento con tamaño intrínseco (una `<img>`) no estira su celda y `text-align` no lo mueve. Este bug ya pasó una vez (logo pegado a la izquierda pese a `items-center text-center`) — revisar esto antes de asumir que un header está centrado.
- **No fabricar datos**: ninguna pantalla muestra números, gráficas o listas inventadas. Si el dato real no existe todavía (backend sin ese módulo), se omite o se marca explícitamente como pendiente en texto, nunca con un placeholder que parezca un valor real.
- Todo tweak de layout/color pasa por las clases de Tailwind y los tokens de `globals.css` — no `style={{ color: '#...' }}` inline salvo casos ya existentes justificados (ej. el swatch de color de un producto, si algún día se agrega).
